### AC-01 · CRITICAL · CONFIRMED · `core/agent.py:710`
**The Telegram conversational tool-use path gates on 'is this a known team member' (inbound_filter sender verification), not 'is this Eyal' — any verified team member's plain-text chat can directly modify live approved data (update_task, rollback_gantt_update, process_quick_injection) with zero is_eyal check anywhere in the call chain, and this is exactly the path the office manager inherits the moment she is added as a recognized sender.**

- **Failure scenario:** A message from any Telegram user whose telegram_user_id is in TEAM_TELEGRAM_IDS passes guardrails/inbound_filter.check_inbound_message (verify_sender_telegram only checks team-roster membership, not identity==eyal) and reaches telegram_bot._handle_message's fallback at line ~3149-3162, which calls _route_inbound_text -> core/agent.py process_message(user_id=<that member>) with no is_eyal branch anywhere in process_message (line 223) or ConversationAgent.respond (core/conversation_agent.py:54, tool_executor invoked at line 140 with only tool_name/tool_input, no actor). The tool loop can invoke _tool_update_task (agent.py:710, calls supabase_client.update_task directly — no approval gate, no confirmation) or _tool_rollback_gantt_update (agent.py:1040, calls gantt_manager.rollback_proposal directly with no approval step). Concretely: Roye (or, once onboarded the same way, the office manager) types 'mark task <id> as done' or 'undo the last Gantt change' to the bot and the change lands live — no approval, no Eyal involvement, violating the 'Gianluigi proposes, Eyal approves' invariant (I1) and I16(b) ('gate on Eyal specifically, not a known/team human').
- **Suggested fix:** Add an explicit is_eyal (or role>=admin) check before executing any write-capable tool inside _execute_tool_call (create_task/update_task/rollback_gantt_update/process_quick_injection), or maintain a separate read-only TOOL_DEFINITIONS subset for non-Eyal senders and route all writes from non-Eyal users through submit_for_approval the same way propose_gantt_update already correctly does.  _(effort: M)_

### TS-01 · CRITICAL · CONFIRMED · `services/telegram_bot.py:1554`
**Telegram /search, /decisions, and /questions command handlers send DB content to whichever chat invoked them with zero sensitivity filtering and zero identity gate.**

- **Failure scenario:** `_handle_search` (telegram_bot.py:1554-1667) calls `supabase_client.search_embeddings(...)` directly and formats/sends the raw hits via `self.send_message` — no `filter_by_sensitivity` call anywhere in the function, and (unlike `_handle_message`) no `sanitize_outbound_message` call either. `_handle_decisions` (line 1668-1692) calls `supabase_client.list_decisions()[:10]` — a plain approval-status filter with no sensitivity filter — and posts every field (including CEO-tier decisions on cap table/legal/investor terms, now that the semantic index also carries curated decision text) straight to `update.effective_chat.id`. None of the three handlers check `is_eyal` (contrast with `_handle_retract`/`_handle_review`/callback handlers at telegram_bot.py:1917-3019 which do). CommandHandler registration (telegram_bot.py:440-457) applies no `filters.Chat(...)` restriction, so any chat the bot is a member of — including the group chat (-5187389631) or a future DM from the office manager — can issue `/decisions` or `/search <query>` and receive FOUNDERS/CEO-tier content verbatim. This is exactly the I16(1)/I3 scenario: a new, lower-clearance recipient receiving CEO-level output.
- **Suggested fix:** Gate these three handlers on `is_eyal` (reject/redirect non-Eyal senders, matching the pattern already used elsewhere in this file), and independently apply `filter_by_sensitivity(...)` (capped to the sender's actual clearance, not hardcoded CEO) to every result list before formatting, mirroring what `mcp_server.py`'s `search_memory` and `processors/meeting_prep.py` already do.  _(effort: S)_

### AD-01 · HIGH · CONFIRMED · `processors/sheets_sync.py:968`
**reconcile_tasks/reconcile_decisions rewrite the per-row snapshot with the edited value even when the DB write for that edit failed, so the edit is silently reverted on the next cycle with no retry and no alert.**

- **Failure scenario:** Eyal edits a task's Assignee cell in the Tasks sheet (Roye -> Paolo). reconcile_tasks (processors/sheets_sync.py) detects sheet!=snapshot!=db, classifies it as 'Eyal edited', queues db_updates[sid]={'assignee':'Paolo'} and unconditionally computes final['assignee']='Paolo' for the snapshot (lines 767-771, 841-844). At APPLY time, supabase_client.update_task(sid, assignee='Paolo') throws (transient Supabase/network error, PostgREST 5xx, idle-wake broken pipe) -> caught at line 967-969, added to db_update_failed, but db_update_failed is ONLY consulted afterward to filter archive_moves (lines 973-977) -- it is never used to skip or adjust snapshot_writes. Step 4 (lines 1042-1047) unconditionally calls supabase_client.upsert_sheet_snapshot(sid, ..., 'Paolo', ...), recording the snapshot as if the edit landed, while the DB still has 'Roye'. Next reconcile cycle: sheet('Paolo')==snapshot('Paolo') so the 'Eyal edited' branch no longer fires; the code falls into the 'DB advanced -> refresh Sheet from DB' branch (db_val 'Roye' != sheet_val 'Paolo') and queues a cell write that overwrites the Sheet cell back to 'Roye' -- silently discarding Eyal's edit with no error surfaced. Identical pattern exists in reconcile_decisions (content-field loop appends snapshot_writes unconditionally at lines 1229-1231; the DB-update loop at 1254-1266 has no failure-tracking set at all before the unconditional snapshot rewrite at 1309-1312), so a Decision text/label/rationale/confidence edit can be silently reverted the same way.
- **Suggested fix:** Track failed task/decision ids from the DB-update loop (reconcile_tasks already builds db_update_failed; reconcile_decisions needs the same set added) and skip -- or write a snapshot reflecting the PRE-edit DB values for -- any row whose update failed, so the next cycle re-detects the edit as pending and retries the pull instead of reverting it. Also log a WARNING/alert (not just a debug-level swallow) so a persistently-failing pull is visible.  _(effort: S)_

### TS-02 · HIGH · CONFIRMED · `core/agent.py:721`
**The conversational agent's search_memory tool (reachable by any Telegram sender via free text, not just Eyal) returns raw, sensitivity-unfiltered decisions/topics/embeddings, unlike the MCP search_memory tool which explicitly filters.**

- **Failure scenario:** `GianluigiAgent._tool_search_memory` (core/agent.py:721-740) calls `supabase_client.search_memory(...)` and returns the dict (`embeddings`, `decisions`, `tasks`) verbatim with no `filter_by_sensitivity` call — contrast with `services/mcp_server.py:433-440` which explicitly applies `filter_by_sensitivity(results['embeddings'], 4)` before returning, with a comment noting this exists specifically "to protect any future lower-tier caller." `telegram_bot.py._handle_message` (the general text handler) routes ANY sender's free-text message to this agent when it isn't one of the `is_eyal`-gated special flows (telegram_bot.py:3143-3162) — there is no `is_eyal` check before line 3143. The only mitigation is `sanitize_outbound_message` (inbound_filter.py:325-353), which is a hardcoded REGEX pattern match for known-sensitive strings (salary/equity/term-sheet phrasing) — not a tier-based filter — so a CEO-tier decision/topic surfaced by the agent's tool call whose text doesn't match those specific patterns (e.g. a competitor-intel narrative, a board discussion summary, a hiring-plan decision) passes through untouched to a non-Eyal sender.
- **Suggested fix:** Thread a caller-identity-derived `max_sensitivity_level` into `_tool_search_memory` (and `search_memory` itself) and apply `filter_by_sensitivity` to all three result buckets (embeddings, decisions, tasks), not just embeddings as MCP does today.  _(effort: M)_

### SS-01 · HIGH · CONFIRMED · `services/gmail.py:179`
**Gmail's send-email write path uses a generic @retry decorator that never rebuilds the httplib2 transport, so a post-idle-wake broken pipe fails identically on all 3 attempts, then send_email() swallows the exception to `False` which most callers ignore.**

- **Failure scenario:** services/gmail.py:81-126 (`_execute_with_retry`, used for reads) explicitly nulls `self._service = None` between attempts specifically to rebuild the stale httplib2 socket after a Cloud Run idle-wake cycle (per CLAUDE.md's documented broken-pipe pattern). But `_execute_send` (gmail.py:179-196), which backs `send_email()` (the write path used for approval emails, meeting-prep emails, weekly-review distribution emails, and email_watcher replies), is instead decorated with `core/retry.py`'s generic `@retry(max_attempts=3, backoff=2.0)` (retry.py:52-73), which has no access to `self` and never resets `self._service`. On an idle-wake BrokenPipeError, `self.service` (the memoized property) stays bound to the dead transport for all 3 attempts, so every retry fails the same way and `send_email()` (gmail.py:261-263) catches the final exception and returns `False`. Compounding this: `guardrails/approval_flow.py:2616-2621` and `:3207-3212` call `await gmail_service.send_email(...)` and then unconditionally set `results["email_sent"] = True` immediately after, regardless of the return value — so even the boolean failure signal is discarded, and the approval-flow audit record falsely claims the email went out. `schedulers/email_watcher.py:522` likewise ignores the return value for the team-member reply path.
- **Suggested fix:** Make `_execute_send` null `self._service` between attempts the same way `_execute_with_retry` does (either move the send call through `_execute_with_retry`'s request_factory pattern, or add a local retry loop mirroring it). Separately, fix approval_flow.py:2621 and :3212 to set `email_sent` from the actual boolean return value of `send_email()`, and alert Eyal when it's False instead of recording silent success.  _(effort: S)_

### SS-02 · HIGH · CONFIRMED · `schedulers/document_watcher.py:202`
**A transient (post-retry-exhausted) Drive download failure for a binary document is treated as a terminal, un-alerted quarantine on the very first poll, bypassing the poison-threshold+alert mechanism the scheduler otherwise uses for real failures.**

- **Failure scenario:** `services/google_drive.py:294-311` (`download_file_bytes`) and `:363-384` (`download_file`) both internally retry 3x on transient errors (nulling `self._service` correctly) but on exhaustion CATCH the exception and return a sentinel (`b""` / `""`) instead of raising — per their own docstrings, 'empty on failure after retries'. `schedulers/document_watcher.py:_process_new_document` (lines 199-220) treats that sentinel identically to a genuinely-empty/unextractable file: line 202-210 for binary files (`if not file_bytes: drive_service.mark_document_processed(file_id); return {...status: error}`) and line 213-220 for the no-text-extracted case both call `drive_service.mark_document_processed(file_id)` directly and RETURN a plain dict — no exception is raised. This means `_poll_once` (document_watcher.py:132-176), whose try/except at line 135-159 implements the sanctioned P4-04 pattern (3 poll-cycle failures -> `alert_critical_error`, only then quarantine), never sees this failure at all: no `alert_critical_error` call fires, and the document is permanently marked processed (`_processed_doc_ids.add`) after a SINGLE poll, on the first sustained network blip (e.g. exactly the idle-wake broken-pipe scenario the retry wrapper exists to survive, if it outlasts the ~2+4s internal backoff). The document is silently lost from Gianluigi's knowledge for the container's uptime with zero operator visibility.
- **Suggested fix:** Have `download_file`/`download_file_bytes` raise (rather than swallow to a sentinel) when retries are exhausted, OR have document_watcher distinguish 'download failed' from 'genuinely empty' (e.g. by having the download functions return a sentinel object / raise a dedicated exception) and route the failure path through the same raise-and-let-`_poll_once`-catch-it pattern used for every other error, so it gets the 3-strike + alert treatment instead of an unannounced one-shot quarantine.  _(effort: S)_

### SS-03 · HIGH · CONFIRMED · `guardrails/gantt_guard.py:123`
**is_protected() treats a transient Supabase read failure identically to 'row genuinely not protected', so a network blip during Gantt-proposal validation can let a write to a protected/formula row pass validation with no re-check at execute time.**

- **Failure scenario:** `_load_schema()` (gantt_guard.py:45-52) wraps its Supabase call in try/except and returns `[]` on ANY exception, logging only. `is_protected()` (gantt_guard.py:123-133) calls `_load_schema()` fresh (a brand-new network round trip, no caching) and returns `False` (not protected) whenever the schema list is empty — which is indistinguishable from 'the read just failed'. `validate_proposal()` calls `is_protected()` once per changed cell inside its loop (gantt_guard.py:339), so a proposal with N cells makes N independent Supabase calls to `_load_schema()`, any one of which failing transiently silently defeats the protection check for that cell (all other checks in `validate_proposal` still run against the successful first `_load_schema()` call at line 261, so the proposal is NOT globally rejected — only that one row's protection silently evaporates). `services/gantt_manager.py:propose_gantt_update` (line 726) calls `validate_proposal()` exactly once at proposal-creation time and — per the June 2026 audit note in SYSTEM_AUDIT_2026_06.md — there is no execute-time re-validation (confirmed: no second `is_protected`/`validate_proposal` call anywhere in gantt_manager.py), so this is the only gate before a formula/header row can be overwritten once Eyal approves the (incorrectly-validated) proposal.
- **Suggested fix:** Load the schema ONCE per `validate_proposal()` call (already done at line 261) and pass those `schema_rows` into `is_protected()`/`resolve_row_number()` instead of having each call re-fetch; if a fetch legitimately fails, propagate the exception (or an explicit 'validation could not run' state) so `validate_proposal` fails CLOSED (rejects the proposal) rather than silently treating an unknown row as unprotected.  _(effort: S)_

### SC-01 · HIGH · CONFIRMED · `schedulers/intelligence_signal_scheduler.py:90`
**The weekly/nightly sleep-until schedulers set their in-memory 'already ran this period' guard unconditionally after calling a helper that swallows its own exceptions, so ONE failed run (no restart needed) silently skips generation for the entire remaining week/day.**

- **Failure scenario:** In intelligence_signal_scheduler.py, `_run_generation()` (line 134-175) wraps `generate_intelligence_signal()` in its own try/except and never re-raises -- it only logs, heartbeats status='error', and calls check_and_alert. Back in the main loop, line 90-91 does `await self._run_generation(); self._last_generated_week = week_key` UNCONDITIONALLY -- there is no branch on success/failure. So if Thursday 18:00's LLM call throws (rate limit, transient Anthropic 5xx, DB timeout), `_last_generated_week` is still set to the current week, and the outer `except Exception` / 5-min-cooldown-retry path (line 95-97) never fires because nothing escaped `_run_generation()`. The weekly intelligence signal is then silently dark until next Thursday -- indistinguishable from 'nothing newsworthy this week' to Eyal. The identical pattern exists in knowledge_weekly_scheduler.py:63-64 (`await self._run(); self._last_generated_week = week_key`), which drives BOTH topic synthesis AND `decision_synthesis`/`decision_clustering` -- this is exactly the 'decision-synthesis missed-Sunday-run' failure class from project memory, but a distinct root cause from the previously-fixed 'flag enabled after the window' incident: this one needs no restart at all, just one failed LLM/DB call inside a long-lived Cloud Run process (min-instances=1).
- **Suggested fix:** Have `_run_generation()`/`_run()` return a success bool (or re-raise), and only set the fire-once guard (`_last_generated_week`/`_last_run_date`) when the run actually succeeded; on failure, fall through to the outer except's short cooldown-and-retry within the same trigger window (or explicitly schedule a same-day retry) instead of silently deferring to next period.  _(effort: S)_

### RG-01 · HIGH · CONFIRMED · `services/gantt_rows.py:86`
**The Gantt row-tag identity module (`gantt_rows.py`, built after the June audit) calls `sheets_service.service.spreadsheets()...execute()` directly for both reads and writes, bypassing `sheets_service._execute_with_retry` entirely — reintroducing the exact P3-07 bare-`.execute()` class the June fix-PR closed in `google_sheets.py`/`google_drive.py` proper.**

- **Failure scenario:** `read_row_tags` (gantt_rows.py:57-62) and `write_row_tag` (86-91) reach into `sheets_service.service` (the raw googleapiclient object) instead of `sheets_service._execute_with_retry`, so neither retries nor rebuilds the transport on a stale idle-wake socket. Concretely: Eyal approves a `gantt_tag_mapping` proposal via `decide_proposal` (mcp_server.py:787-793); `apply_row_tags` (processors/gantt_tagging.py:109-123) calls `write_row_tag` for each mapping — on the first post-idle broken pipe it raises, is caught, returns `False`, and `apply_row_tags` silently skips that mapping (no exception, no partial-failure alert). mcp_server.py:791 then unconditionally calls `supabase_client.delete_pending_approval(proposal_id)` regardless of whether `applied < len(mapping)` — the proposal is gone, so it can't be retried. Eyal is told he approved a tag mapping; some or all of it silently never wrote to the Sheet.
- **Suggested fix:** Route `read_row_tags`/`write_row_tag`/`format_tag_column` through `sheets_service._execute_with_retry` (mirror the pattern already used elsewhere in `google_sheets.py`); in `apply_row_tags`/`decide_proposal`, only delete the pending approval and report success when `applied == len(mapping)`, otherwise keep it pending and alert.  _(effort: S)_
